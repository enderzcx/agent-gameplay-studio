# 配音设计（解说口播的声音层）

`references/postproduction-standard.md` §5 只规定了**流程**（开场、有停顿、逐事件生成、测实长、字幕来自口播稿），
**没有规定声音本身**。本文件补上那一层：角色、发音、控制手段的真实效力、引擎参数边界、验收口径。

本文件是 `contract` 类 skill 的 `references/` 一员，只描述**要什么、怎么验、哪些做不到**；
不提供剪辑/合成脚本（按 SKILL「故意不加」，执行交给 `editor`）。

---

## 1. 固定角色（voice profile）——每支片子必须先定

不许"随便找个声音念稿"。先写死六项，再写台词：

| 项 | 要求 |
|---|---|
| 身份 | 第一人称玩家本人 / 旁观解说 / 游戏内角色——三选一，不许混 |
| 性别与年龄感 | 具体到区间（例：男，20–26 岁听感） |
| 音色 | 中高音区还是胸腔低音；清亮还是浑厚 |
| 性格 | 例：清楚、认真但**不装高手** |
| 情绪基线 | 必要时给出允许的情绪上限（例：只在险境短暂收紧，不满篇亢奋） |
| 失误处理 | 例：克制自嘲，一两句，不反复卖惨 |

**事后复盘的边界**：`retrospective_commentary` 是**事后**说的，不许表演成"当时的心理活动"。
台词里也不许把五要素逐条念出来（§3.1 同义要求）。

## 2. 发音词典——必须单独写，且必须现场核

术语、数字、英文专名各一张表。**书面写法 ≠ 口播写法**：

- 去书面化：`施加易伤状态` → `把易伤挂住`；`进行防御` → `防御`；`生命值` → `血`
- 卡名/角色名：照念，不改字
- 数字：统一用阿拉伯数字，便于与字幕逐字核对
- 英文专名：**默认避免**。本机实测英文名在中文 TTS 上会被读错
  （基线样片把 `MiMo` 读成「麦猫」）

**多音字是必查项，不是可选项。** 本机实测：`白挨` 的 `挨` 被读成一声 `āi`，
而口语语境应为二声 `ái`；TTS 词典不按上下文消歧。
**最稳的做法不是写进词典，而是改写文案绕开多音字**（`白挨` → `硬吃`），
因为词典条目能否生效**必须逐条实测**，不能假定写入即生效。

## 3. 导演提示（director notes）的真实效力——**不要假定它生效**

逐语义段写节奏/重音/停顿/情绪意图是有用的**意图文档**，但：

> **本机实测（2026-09-23）：一次 2×2 小对照没能证明"有导演提示"稳定压过随机性。
> 这是"尚未证明有效"，不是"已证明无效"。**

证据：同一句台词、同一音色、同一音量归一化，做 2×2（有/无导演提示各两次）盲听：

| 槽位 | 条件 | 时长 | 盲听 |
|---|---|---|---|
| 1 | 无提示 | 3.84 s | 偏快干脆，最像随口 |
| 2 | 有提示 | 4.32 s | 中速从容 |
| 3 | 无提示 | 5.44 s | 慢速、戏剧化、带叹息 |
| 4 | 有提示 | 6.40 s | 偏慢、夸张，最不像随口 |

盲听按相似度分成 {1,2} 与 {3,4} 两组——**分组与"有无提示"不一致**；
同条件两次生成的差值（1.6 s）大于条件间平均差。

**能说什么**：在 n=1、每格 2 次的小样本下，**没有观察到稳定的提示效应**（未做显著性检验），
所以"写了提示就一定会那样念"是没有依据的。
**不能说什么**：不能据此断定该字段无效、更不能推及"引擎能力边界"——
单次小样本既不能证明有效，也不能证明无效。

**官方文档（`quick-start/usage-guide/audio/speech-synthesis-v2.5`）明确声明支持风格控制**，且提供两条通道：

1. **自然语言控制** → 放在 `role: user` 的 `content`（内置声线也支持）。文档称
   "a single natural language instruction is sufficient to take effect"，并支持**导演模式**
   （Character / Scene / Guidance 三维：身份性格、当下情境、语速呼吸停顿重音共鸣情绪波动）。
2. **音频标签控制** → 放在 `role: assistant` 的 `content`：开头 `(风格)`，
   句中可插 `[吸气]`/`[叹气]`/`[笑]`/`[放慢]` 等细粒度标签。
   `user` 的内容**不会出现在合成语音里**，所以导演稿不会被念出来。

**实践口径**：导演提示**该写**（它是可复现的意图记录，也是官方推荐通道），
但**必须逐条用听感验证是否真的生效**，不能凭"API 接受了"就当成已生效；
也不要因为一次小样本没测出差异就把这条通道判死。

另外两条**不依赖提示**、始终可用的手段：
1. **文本层**：短句、句号收束、避免并列顿号列表（"报菜名"是最典型的机器腔来源）；
2. **重试层**：每段多 take，**按听感挑选**。

## 4. 引擎与配置（本机实测的通路）

一次基线片记录过某个"语音网关"的调用，但**用当时的测试方法与凭据没能复现**：
`GET {base}/models` 只列出非音频模型，`GET /v1/audio/{speech,voices,models}` 返回 404，
企业/控制台前缀返回 HTML。

> **这三条不能推出"该网关没有语音能力"。**
> `GET /v1/audio/speech` 404 只说明该 **GET** 路径不存在，**不能证明对应的 POST 路由不存在**；
> 模型列表里没有音频模型，也不等于账号或该端点不支持音频。
> 而且**没有任何证据**表明旧调用来自网页 console —— 那只是当时的一种推测。
> 正确写法只有一句：**"本轮测试方法与凭据未能复现该调用"**，其余为未知。
> **通用纪律：没复现 ≠ 不存在。**不要把一次失败的探测写成能力结论。

实测可用的形状是 `chat/completions + audio`（**不是** `/v1/audio/speech`）：

```
POST {TTS_BASE_URL}/chat/completions      # 你自己端点的 base，例如 https://your-endpoint.example/v1
Authorization: Bearer $TTS_API_KEY
{
  "model": "<你的 TTS 模型 id>",
  "messages": [ {"role":"assistant","content":"<要念的文本>"} ],
  "audio": {"format":"wav", "voice":"<声线 id，可选>"},
  "stream": false
}
→ choices[0].message.audio.data  (base64)
```

> **本仓库不附带端点、密钥或额度。**`tools/voice/tts_adapter.py` 是**可选外部适配器**：
> 你必须自己提供 `TTS_BASE_URL` 与 `TTS_API_KEY`，它才可能跑起来；
> 装上本仓库**不会**让你具备任何模型能力。下面这张表是**该形状实测到的一组参数**，
> 仅作为"要核哪些字段"的清单；**换端点必须重新核对，不要照搬**。

| 参数 | 实测情况（某 `chat/completions + audio` TTS 端点） |
|---|---|
| `model` | 一个内置声线模型 / 一个"文字描述生成声音"的 voicedesign 模型 / 一个需要音频样本的 voiceclone 模型 |
| `audio.format` | `wav`（默认）/ `mp3` / `pcm` / `pcm16`（流式必须 `pcm16`） |
| `audio.voice` | 仅内置声线模型接受声线 id；**voicedesign 不支持该字段**；voiceclone 只接受样本 base64 |
| `audio.optimize_text_preview` | 仅 voicedesign 支持；置 `true` 时 `assistant` 消息可省略（会智能润色文本） |
| **风格/情绪/语速控制** | **没有独立的数值参数**，但有两条受支持的通道：`user` 消息的自然语言（含导演模式）、`assistant` 文本里的 `(风格)` 与 `[吸气][叹气]` 等标签 —— 见 §3。是否**真的生效**必须逐条听感验证 |
| `messages` 里的 `user` 提示 | voicedesign 下**必需**；普通 tts / voiceclone 下可选。文档称 `user` 的内容**不会出现在合成语音里**，所以导演稿不会被念出来 |
| `stream` | 内置声线模型支持低延迟流式；voicedesign / voiceclone 只兼容模式（推理完一次性返回） |
| 输出采样率 | 24 kHz mono |

**声线必须按听感选，不能按名字猜。** 本项目曾对同一批内置声线做同句盲听表征，
最后选了其中一个青年男声（当时评价是"接近玩家随口即兴解说"）。
**那是一次本地试验的结论，不是你的默认值，也不是任何人的永久偏好** ——
本仓库刻意不为 `TTS_VOICE` 设默认值，请自己听着选。

**凭据**：只从环境变量（或你可选指定的 env 文件）读取，**不打印、不写进产物、不进日志**。

## 5. 混音与交付口径

标为**本项目目标**，不是全平台标准：

| 项 | 目标 |
|---|---|
| 旁白整轨响度 | **−16 LUFS** |
| true peak | ≤ **−1.5 dBTP** |
| 中间产物 | 无损 WAV / PCM（24 kHz 合成 → 48 kHz 终混） |
| 原声 | 源片有原声则旁白时压低并保留关键动作；**源片无音轨就如实静音，不伪造** |

本机基线片实测仅 **−23.5 LUFS**（LRA 5.4 LU），明显偏小——这是**可复现的客观缺陷**，不靠听感也能判。

## 6. 逐段量产方式

- 按**语义段**切分，一段一次请求；`tts_text` 与 `subtitle_text` **分列**（字幕来自实际口播稿，不是另写文案）。
- **内容寻址缓存**：改动一句只重做那一句，不整体重跑。
- **逐段实测时长**（ffprobe），不要估算；旁白**压在画面之上**，不是画面播完再念。
- 每段旁白时长必须 ≤ 该段画面时长；超了就是硬错，构建时应报错。

## 7. 验收：人工与机器必须分开写

| 验收方式 | 能得到什么 | **不能**得到什么 |
|---|---|---|
| 机器听感（`gemini-companion` 原生读文件） | 读音/多音字错读、停顿位置、句尾拖长、重音落点、接句生硬、指令残留、机械感线索 | 人类留存、受欢迎程度、审美定论 |
| 客观测量（`ffprobe` / `ebur128`） | 时长、采样率、响度 LUFS、LRA、true peak | 像不像真人 |
| 源帧核对 | 音画是否错配、选牌/胜负等硬事实 | 声音好不好听 |

**硬规则**：

- **16 kHz / mono 不是"机器感"证据**——那是带宽指标。机器感只能由气息/停顿/重音/情绪曲线等线索支撑。
- 单一模型的一次听感是**意见**，方向可信、强度不可当定论；不得用模型分数替代人类试听，不得据此断言留存。
- 审听用**原生纯音轨**（可包在无文字纯色画面里）时，**不要把字幕或原稿喂给评审**，否则无法排除"读字幕冒充听懂"。
- 音画错配要回源帧核对（见 `references/spire-checklist.md` 的本地口径）。
- 审听提示必须**中立**：不暗示期待好评。
